# Campaign delivery boundary — offline draft

Status: locally implemented packing, not an activated dataset or Android route.
This document specifies the next consumer boundary without authorizing a new
collector scope, upload, credentials change or public eligibility claim.

## Small index and self-contained details

`prepare-campaign-delivery.mjs` takes the same independently pinned inputs as
`prepareCampaignPreview`. It does not accept an arbitrary preview object. It
reuses the bounded observation and static-definition validation before packing.

- Index: schema 1, `dokkan-campaign-index-preview`, at most 32 KiB expanded.
- Detail: schema 1, `dokkan-campaign-detail-preview`, at most 512 KiB expanded
  per campaign. Only that campaign's referenced missions and completion mission
  are included, deduplicated within the file.
- All generated bytes together: at most 4 MiB. Oversize input fails as a unit;
  no truncated index or partially returned bundle.
- JSON UTF-8 bytes are hashed exactly as generated. Returned metadata includes
  the index SHA-256, each detail SHA-256 and exact expanded sizes.
- Every document carries region `global`, observation/definition/database hashes,
  observation time, exclusive freshness limit and explicit offline/partial
  authority. Source metadata is not player progress or availability authority.

The index is a separate experimental artifact, **not** the current Home feed.
A future Home adapter selects a small subset of summaries and must still obey
the existing Home 65,536-byte cap. It must not copy every mission into Home or
raise the cap to accommodate this feature.

## Typed destination proposal

Each index entry has a title, optional visible deadline, board count, detail
hash/size and a destination `{type: "campaign-detail", campaignId, detailSha256}`.
There is no raw URL, filename, executable route or stage-area ID. A future
Android route must use this new campaign destination, not existing event missions.
Titles and descriptions are inert text; displayed text is never interpreted as
a link. Reward references remain typed item definitions, not navigation targets
until their existence is validated against the relevant consumer catalog.

## Consumer and publisher gates — not implemented yet

1. Obtain a fresh, explicitly scoped observation. Historical replay is test
   evidence only. The account observation is partial and must not be labeled as
   all campaigns available to every user.
2. Define and review a public schema separately. Do not strip
   `publicationAllowed: false` or promote these preview contracts unchanged.
3. Publish validated immutable details first; update the index/manifest last.
   Publication requires a separate authorized dry-run and byte report. Neither
   this packer nor its tests perform writes to storage or the network.
4. The client accepts index bytes only after an independently trusted manifest
   hash and size match. It rejects unknown versions/destinations, invalid bounds,
   duplicates, wrong region and invalid timestamps; an old app ignores the
   optional campaign feature without disturbing summons/events.
5. On selection, fetch only the chosen detail from the configured dataset origin
   using a locally constructed content-hash key. No server-provided arbitrary
   URL, cross-origin redirect or credential belongs in this mechanism.
6. Verify the downloaded byte cap, exact size/hash, schema, campaign ID, source
   identities and observation interval against the selected index snapshot.
   Keep that snapshot attached to the request: a refreshed index must not relabel
   an in-flight response. Switching cards/campaigns cancels or isolates old work.
7. Cache by region + schema + detail hash, not campaign ID alone. Verify cached
   bytes on reuse. Restore a destination only against a matching verified index;
   if expired, refresh first. A missing/deleted campaign or failed detail request
   affects only that destination, not Home. Expired data must not regain a live
   label merely because immutable bytes remain cached.

UI layout, loading/error copy, cache eviction budget, public manifest keys and
fresh collection integration remain separate implementation gates. No progress
tracking, remaining-reward total or automatic reward-link resolution is implied.

## Historical measurement and verification

Replay of the provided September 11 observation at its original timestamp:
6 campaigns; index **2,529 bytes**; details **52,579 / 18,146 / 12,011 / 10,332 /
5,316 / 9,496 bytes**; total **110,409 bytes**. This only measured in-memory
packing; no new game request or publication occurred.

Focused tests cover exact hashes/sizes, provenance parity, typed destinations,
mission isolation/deduplication, deterministic identity, invalid pins, exclusive
expiry, private-wrapper omission and all three byte budgets. Independent
read-only review reported no material finding in the packing boundary.

## Cross-language synthetic fixture

`fixtures/generate-campaign-consumer-fixture.mjs <explicit-output-directory>`
generates two synthetic campaigns through this actual packer, along with exact
index/detail pins. Existing identical files are retained; conflicts fail without
overwriting. It reads no account capture or game database and makes no requests.
The Android fixture location is `app/src/test/resources/campaign-preview` in
the active Android worktree. This receipt is test evidence, not a public
manifest. Android consumer work is isolated under `data/home/campaigns` and
does not enable this preview in Home or authorize remote delivery.

Android follow-up: the isolated preview parser/cache/injected-source loader has
passed compilation and focused tests, including these generated fixtures and
out-of-order responses. The parser suite also passed a strengthened canonical
instant regression. Independent read-only review reported no material issue.
No concrete HTTP source, Home DI/navigation, manifest or public dataset is wired.
Consumer details are documented in Android `docs/features/home-campaign-consumer.md`.
